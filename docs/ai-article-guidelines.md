# HOBNOVA AI記事制作ガイドライン

この文書は、AIエージェントがHOBNOVAのコンテンツを企画し、調査・執筆・画像制作・実装・検証を
一貫して行うための運用手順である。ルートの `AGENTS.md` から参照されるため、短い記事制作依頼でも
必ず適用する。既存の設計・ブランド・実装方針は `README.md`、`CLAUDE.md`、
`src/content.config.ts`、`src/consts.ts` を正とし、この文書はそれらを置き換えず、記事制作時の判断と
品質ゲートを補う。

## 1. 作業開始時に確認するもの

次の順で現状を確認する。過去に読んだ内容やこの文書の例だけで判断せず、リポジトリの現在の状態を
優先する。

1. 適用範囲内のすべての `AGENTS.md` と、`README.md`、`CLAUDE.md` を読む。
2. `src/content.config.ts` と `src/consts.ts` で、現在のschema、カテゴリID、URL規則を確認する。
3. 対象collectionの既存コンテンツを列挙し、frontmatterと本文を読む。タイトルだけでなく、扱った
   問い、結論、比較対象、データまで確認して重複を判定する。
4. `src/components/ui/ImagePlaceholder.astro`、各layout、一覧・TOPの画像呼び出しを確認し、画像の
   表示用途とクロップを把握する。
5. `.github/workflows/` と `scripts/README.md` を確認し、現在のPR・Preview・通知フローに従う。
6. ページ、Astroコンポーネント、Content Collections、スタイルに変更が及ぶ場合は、`AGENTS.md` が
   指定する該当Astro公式ガイドを先に参照する。

## 2. テーマ選定

テーマは次のいずれかに明確に属するものだけを選ぶ。

| 表示カテゴリ | 実装先 | 識別方法 |
|---|---|---|
| CAMP | `src/content/articles/` | `category: "camp"` |
| GADGET | `src/content/articles/` | `category: "gadget"` |
| DIGITAL MARKETING | `src/content/articles/` | `category: "marketing"` |
| DATA LAB | `src/content/data-lab/` | `dataLab` collection（`category`なし） |
| TOOLS | `src/content/tools/` | `tools` collection（`toolId`必須） |

候補を複数考え、次の優先順位で1つに絞る。

1. 読者が実際に検索したくなる具体的な疑問に、明確な答えを返せる。
2. 比較、実測・検証、公開データ分析、条件別の判断、または2026年時点の変化を示せる。
3. 一次情報を十分に確保でき、HOBNOVA独自の整理・計算・考察を加えられる。
4. 既存記事と検索意図、結論、主要な比較軸が重複しない。既存記事の単なる言い換えや、薄い派生を
   選ばない。
5. HOBNOVAの「試す・調べる・分析する・作る」の少なくとも1つを実践できる。

検索需要を意識しても、検索ボリュームを未調査のまま断定しない。時事性だけを理由に選ばず、公開後も
読者が判断や行動に使えるテーマにする。TOOLSは解説記事だけでは完成せず、実際に動作するツール実装が
必要である。DATA LABは、出典を追跡できないサンプル値や推測値を公開データとして使わない。

## 3. Web調査と事実確認

製品仕様、価格、サービス内容、制度、法律、統計、市場、ソフトウェア、2026年の状況など、変更される
可能性がある内容を含む場合は必ずWebで再調査する。比較記事では比較対象を同じ基準日・条件に揃える。

### 情報源の優先順位

1. 官公庁、公的統計、法令、規格、原典となるデータセット
2. メーカー・サービス運営者の公式仕様、料金表、リリース、公式ドキュメント
3. 査読論文、調査主体が方法と母数を開示した報告書
4. 信頼できる報道・専門媒体（一次情報を補足するとき）

検索結果の要約、出典不明のまとめサイト、生成AIの回答だけを根拠にしない。重要な主張は可能なら
複数ソースで照合し、一次情報と二次情報が食い違う場合は一次情報を優先して差異を説明する。

### 記録・引用のルール

- 数値、価格、仕様、対応地域、制度、統計には、本文中で「2026年9月20日確認」など確認日または
  データ基準時点を明記する。公開日を確認日に流用せず、実際に確認した日を書く。
- 計算値は入力値、単位、期間、税の扱い、丸め方、仮定を示し、可能なら再計算する。
- 本文の該当箇所から出典ページへMarkdownリンクを張る。記事末尾に参考資料をまとめる場合も、本文の
  根拠との対応が分かるようにする。DATA LABの`source`だけで出典リンクの代用をしない。
- 引用は必要最小限とし、引用符または引用ブロックで自分の文章と区別する。著作権や各サイトの利用条件を
  守り、表や文章を大量転載しない。
- 推定や独自試算は事実と分けて「試算」「仮定」と明示する。裏付けのない数値、体験、検証結果、製品の
  使用感を生成しない。実機検証をしていない場合は調査比較であることを明記する。
- リンク切れ、リンク先と主張の不一致、単位・桁・合計値を公開前に再確認する。

## 4. 構成・文章・SEO

執筆前に「想定読者」「検索意図」「記事が返す一文の答え」「根拠」「既存記事との差」を定義する。

- `title`は検索意図と記事固有の価値が自然に分かる日本語にする。年号はその年の確認が本当に必要な
  内容にだけ付ける。
- `description`は結論または読めば判断できることを具体的に要約する。タイトルの反復や煽り文句にしない。
- 導入を長引かせず、タイトルを見た読者が知りたい答え・要点を記事前半に提示する。その後に条件、根拠、
  比較、方法、注意点を説明する。
- H2/H3は内容が予測できる見出しにし、検索語を不自然に反復しない。見出し階層を飛ばさない。
- 必要に応じてMarkdown表、箇条書き、具体例、データ、メリット・デメリット、向く人・向かない人、
  独自計算や分析を使う。表はモバイルで列過多にならないようにし、長いセルを避ける。
- SEO目的の前置き、同じ結論の言い換え、網羅性だけを狙った薄い章を増やさない。「いかがでしたか」など
  AI的・定型的な締めや、過剰な煽り、根拠のない最上級を避け、自然な日本語の個人メディアとして書く。
- 関連する既存HOBNOVAコンテンツが読者の次の疑問に役立つ場合は、正しい末尾スラッシュ付きURLで
  文脈に沿った内部リンクを置く。無関係な記事へSEO目的だけでリンクしない。
- 記事本文とfrontmatterに秘密情報、個人情報、APIキー、GitHub Token、LINE Token、環境変数の値を
  書かない。Secretsや`.env`の値を取得・表示しようとせず、ログやコミットにも含めない。

## 5. Content Collectionsへの実装

ファイル名は小文字ASCIIのハイフン区切りとし、そのままslugになる。既存slugと重複させない。URLは
通常記事が`/[category]/[slug]/`、DATA LABが`/data-lab/[slug]/`、TOOLSが`/tools/[slug]/`である。

frontmatterは作業時点の`src/content.config.ts`を必ず確認する。現在の基本形は次のとおり。

```yaml
# articles
---
title: "記事タイトル"
description: "記事固有の説明"
publishDate: YYYY-MM-DD
category: "camp" # camp | gadget | marketing
tags: ["タグ"]
image: "./slug-hero.png"
draft: false
featured: false
---
```

DATA LABでは`category`を使わず、必要に応じて`source`、`stats`、`chart`、`ranking`、`table`、
`explorerId`をschemaどおりに指定する。TOOLSでは`category`を使わず`toolId`を必須とし、対応する
コンポーネントと`src/pages/tools/[slug].astro`の分岐まで実装する。`updatedDate`は既存記事を実際に
更新した場合に使い、新規記事の公開日を重複記載するためには使わない。著者を指定する場合は
`HOBNOVA編集部`とし、個人名を出さない。

schema上の`image`がoptionalでも、**今後制作するすべての通常記事・DATA LAB・TOOLSで画像は必須**と
する。既存コンテンツに画像がないことは、新規コンテンツで省略する理由にならない。

## 6. アイキャッチとサムネイル

### 現在の実装仕様

- 画像はMarkdown/MDXと同じcollectionディレクトリへ置き、`image: "./slug-hero.png"`のような相対
  パスで指定する。`astro:assets`がビルド時に検証・最適化する。`public/`へ記事画像を置いて文字列URLを
  指定する方式へ勝手に変えない。
- 既存の主なhero画像はPNG、1536×1024（3:2）、`<slug>-hero.png`である。ただし、Codex Cloudの
  PR作成経路ではバイナリファイルを扱えないため、**Codex Cloudで今後自動生成する記事画像は、原則として
  テキスト形式のSVG（`<slug>-hero.svg`）にする**。PNG・JPEG・WebPなどのバイナリ画像を新規追加しない。
  ローカル作業などバイナリを安全にコミットできる経路では、用途に適した形式を選んでよい。いずれも
  schemaが読める形式か確認し、SVGでは`width="1536"`、`height="1024"`、`viewBox="0 0 1536 1024"`を
  基本として、十分な表示品質と過度でないファイルサイズを両立する。
- 通常記事とDATA LABの本文heroは16:9、一覧・TOPの通常カードは16:10で`object-cover`表示される。
  Featuredの一部は4:3になる。現在はfrontmatterの同じ1枚をアイキャッチ兼サムネイルとして使う設計で
  あるため、重要な被写体や文字を中央の安全領域へ置き、各クロップで欠けないことを確認する。
- TOOLS画像も同じfrontmatterでカードに表示される。作業時点の詳細layoutでhero表示やOGP利用がない
  場合は、既存設計を確認したうえで必要な表示配線も実装し、「画像ファイルがあるだけ」で完了にしない。

### 制作ルール

画像は記事の問い・比較対象・結論を一目で理解でき、HOBNOVAの白〜ライトグレー、ネイビー／チャコール、
少量のブルーというデザインとカテゴリの雰囲気に合わせる。**単なるプレースホルダー、文字だけの簡易画像、
汎用的な装飾だけの画像は不可**とする。記事固有の内容を、図解、比較対象、道具、データ、利用場面などの
視覚要素で表現する。必要な場合だけ短いタイトル文字や比較ラベルを入れ、小サイズでも読める字量・
コントラストにする。ロゴを変形せず、誤解を招く架空の製品UI、意味のない装飾、過度な宇宙表現を避ける。
SVGを生成する場合も、記事ページの16:9と一覧・TOPの16:10で`object-cover`されることを前提に、主要な
図形・被写体・ラベルを中央の安全領域へ配置し、両方のクロップで意味が欠けない構図にする。

Web画像を無断転載しない。利用できる画像生成機能があれば、記事内容に合わせたオリジナル画像を生成して
リポジトリへ保存する。第三者素材を使う場合はライセンス、改変条件、クレジット要否を確認して記録する。
画像生成機能が使えない、保存できない、または必要な権利を確認できない場合は、存在しないパスや仮画像を
設定しない。画像未生成のため未完成であることを明示し、PR公開・完成通知へ進まない。

生成後は実ファイルの形式、ピクセル寸法、アスペクト比、ファイルサイズ、frontmatterの参照、代替テキスト
として使われるタイトルの妥当性を確認し、ビルド結果をデスクトップとモバイル幅で目視する。

## 7. 自己レビューと検証

実装後、次を1項目ずつ確認し、不備があれば修正して再確認する。

- **回答品質:** タイトルの疑問への答えが前半にあり、対象読者が次の行動を判断できる。
- **事実:** 主張、数値、価格、仕様、日付、計算、単位を原典と照合し、確認時点と仮定が明確である。
- **出典:** リンクが開き、主張を実際に裏付け、一次・公式情報を優先している。
- **独自性:** 既存記事と検索意図・内容が重複せず、比較・検証・分析など独自の価値がある。
- **文章:** 不自然な定型句、冗長なSEO文、重複、誤字、過剰な断定がなく、自然で読みやすい日本語である。
- **SEO:** `title`、`description`、H1/H2/H3、slugが一致した検索意図を自然に表し、キーワードの
  詰め込みがない。
- **内部リンク:** 関連記事がある場合は有用な文脈でリンクし、URLとリンク先を確認した。
- **実装:** collection、frontmatter、日付、category/toolId、slug、画像相対パスがschemaと既存設計に
  適合する。
- **画像:** オリジナルまたは利用許諾済みの実画像が存在し、heroとカードの各比率で意味のある範囲が
  表示され、モバイルでも文字や被写体が欠けない。アイキャッチとサムネイルの両用途を確認した。
- **安全性:** 秘密情報、個人情報、未公開の認証情報が本文、画像、差分、ログにない。
- **表示:** 表、長いURL、見出し、画像、埋め込みUIをモバイル幅を含めて確認し、横溢れや崩れがない。

続いてリポジトリルートで、必ず両方を成功させる。

```bash
npx astro check
npm run build
```

失敗を既存問題として無視せず、原因を切り分ける。環境上どうしても実行できない場合はコマンド、理由、
未確認範囲を明示し、記事を完成扱いにしない。表示に関わる変更では、可能ならビルド済みページまたは
`astro dev --background`を使い、目視確認とスクリーンショットも行う。開発サーバーは確認後
`astro dev stop`で停止する。

## 8. 完成条件

次のすべてが揃った場合にだけ「記事完成」と表現できる。

- [ ] 記事本文または完成したDATA LAB／TOOLSコンテンツ
- [ ] 現行schemaに適合する正しいfrontmatter
- [ ] リポジトリに保存され、実表示を確認したアイキャッチ画像
- [ ] 一覧・TOP等で実表示を確認したサムネイル画像（現行設計では同じ画像の兼用可）
- [ ] 重要な事実・数値・リンク・確認時点の再確認
- [ ] 重複、内部リンク、文章品質、SEO、モバイル表示を含む自己レビュー
- [ ] `npx astro check`成功
- [ ] `npm run build`成功

1つでも欠ければ未完成である。本文だけ、frontmatterだけ、画像パスだけ、仮画像、失敗した検証をもって
完成と報告しない。

## 9. PR・Preview・公開フロー

1. 記事用ブランチで変更し、差分と秘密情報の混入がないことを確認してコミットする。
2. `main`向けGitHub Pull Requestを作る。PR本文にテーマ選定理由、調査・独自分析、主な出典、画像の
   作成方法、自己レビュー、ローカルのcheck/build結果を記載する。
3. `.github/workflows/pr-check.yml`のGitHub Actions（Astro check / build）とCloudflare Pages Previewの
   完了を待ち、Preview URLでデスクトップ・モバイル表示とリンクを確認する。不備は同じPRで修正する。
4. 既存の`article-ready-notification`ワークフローと通知スクリプトに任せる。Secretsの値を読んだり、
   PRコードからLINEへ直接送ったりしない。通知が構成されていない場合も秘密情報を要求しない。
5. AIはPRとPreviewをレビュー可能な状態まで整えるが、`main`へ直接push・mergeせず、本番公開を確定
   しない。**最終Mergeは必ず人間が行う。** Cloudflare Pagesの本番反映は人間のMerge後に行われる。

CIやPreviewが未完了・失敗中の場合は「PR作成済み／確認待ち」と報告し、「公開済み」「完成通知済み」
など事実と異なる表現をしない。
